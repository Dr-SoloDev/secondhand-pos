# WF-06: Cash Control Redesign — ระบบเงินสดและเปิด-ปิดยอด

**สถานะ:** REDESIGN IN PROGRESS — หยุดใช้งาน production ชั่วคราวตามคำสั่ง Owner
**วันที่เริ่มงาน:** 18 สิงหาคม 2569
**ระบบ production ที่ตรวจล่าสุด:** `81d2306`
**ผู้มีอำนาจยืนยัน business rules:** Owner / SoloCorp

เอกสารนี้เป็น source of truth สำหรับการปรับปรุงระบบเปิด-ปิดยอดและ cash control agent หรือ Codex ที่เข้ามาทำงานต่อ ต้องอ่านเอกสารนี้ก่อนแก้โค้ดทุกครั้ง

---

## 1. เหตุผลที่ต้อง redesign

ระบบเดิมทำงานเหมือนมียอดเงินสดอยู่ก้อนเดียว และใช้ยอดนั้นแทนทั้ง:

- เงินรวมของกิจการ
- เงินที่อยู่ในลิ้นชัก
- เงินที่อยู่ในเซฟหรือกับ Owner
- เงินสดที่พร้อมใช้ในวันนั้น

การใช้งานจริงกับแคชเชียร์พบว่า flow ไม่ตรงกับ business logic ของร้าน จึงหยุดใช้ software ชั่วคราวและกลับไปใช้ Excel ระหว่างออกแบบและทดสอบใหม่

ความผิดพลาดนี้เป็น financial-control defect ไม่ใช่เพียงปัญหา UI เพราะอาจทำให้ยอดเงินของกิจการคลาดเคลื่อน

---

## 2. Business model ที่ยืนยันแล้ว

### 2.1 เงินของกิจการมีหลายตำแหน่ง

ยอดเงินรวมของกิจการต้องรวมเงินทุกตำแหน่งที่ยังเป็นทรัพย์สินของร้าน:

- เงินสดในลิ้นชัก (`drawer`)
- เงินสดในเซฟหรืออยู่กับ Owner (`business_reserve` ในระยะแรก)
- เงินในบัญชีธนาคาร (`bank` เมื่อรองรับ ledger ฝั่งธนาคาร)

เงินที่อยู่กับ Owner ยังถือเป็นเงินของกิจการเสมอ ตราบใดที่ยังไม่ได้บันทึกว่าใช้จ่ายหรือเบิกออกจากกิจการ

### 2.2 ลิ้นชักต้องมีเงินเพียงพอ ไม่ใช่มีเงินทั้งหมด

ร้านนำเงินออกจากลิ้นชักเข้าเซฟหรือส่ง Owner ทุกครั้งที่ปิดวัน เพื่อจำกัดความเสี่ยงจากการอุ้มเงินหนีและการปล้น จึงไม่ควรนำยอดปิดวันทั้งหมดมาเป็นยอดที่ต้องนำกลับเข้าลิ้นชักในเช้าวันถัดไป

### 2.3 การย้ายเงินไม่ใช่รายรับหรือรายจ่าย

รายการต่อไปนี้เป็น internal transfer และไม่เปลี่ยนยอดเงินรวมของกิจการ:

- `business_reserve -> drawer` ตอนเปิดวัน
- `drawer -> business_reserve` ตอนปิดวัน

รายการต่อไปนี้เปลี่ยนยอดเงินรวมของกิจการ:

- Owner เติมทุนใหม่
- ซื้อวัสดุ/จ่ายค่าใช้จ่าย
- ขาย Lot แล้วรับเงินสด
- Owner เบิกเงินไปใช้ โดยบันทึกผ่านเมนูค่าใช้จ่ายร้านพร้อมเหตุผล

### 2.4 Owner มีสิทธิ์บันทึกการเบิกผ่านค่าใช้จ่ายร้าน

เฟสปัจจุบันไม่ต้องสร้างฟีเจอร์ Owner withdrawal แยกต่างหาก Owner สามารถบันทึกผ่านค่าใช้จ่ายร้านได้ แต่ต้องระบุจำนวนเงิน เหตุผล และรายละเอียดการใช้เงิน เพื่อให้ยอดและ audit trail ถูกต้อง

ระบบหุ้นส่วน เงินปันผล และสัดส่วนการแบ่งกำไรเป็น phase ถัดไป ไม่อยู่ใน scope นี้

## 3. ตัวอย่าง flow ที่ถูกต้อง

### วันแรก

| เหตุการณ์ | ยอดรวมกิจการ | เงินในลิ้นชัก | หมายเหตุ |
|---|---:|---:|---|
| เปิดวัน | 0 | 0 | ยังไม่มีเงิน |
| Owner เติมทุน 50,000 | 50,000 | 50,000 | เงินใหม่ เพิ่มยอดรวม |
| ซื้อของ 20,000 | 30,000 | 30,000 | เงินสดออกจริง |
| ปิดวัน ย้ายเข้า reserve | 30,000 | 0 | ย้ายตำแหน่ง ไม่ตัดยอดรวม |

### วันที่สอง: Owner นำเงินมาใช้ 20,000

| เหตุการณ์ | ยอดรวมกิจการ | เงินในลิ้นชัก |
|---|---:|---:|
| ยอดยกมา | 30,000 | 0 |
| `business_reserve -> drawer` 20,000 | 30,000 | 20,000 |

กรณีนี้ไม่ใช่เงินขาด 10,000 และไม่ต้องบังคับกรอกเหตุผล เพราะ 10,000 ยังอยู่ใน reserve

### วันที่สอง: Owner นำเงินมา 40,000 จากยอดรวมเดิม 30,000

- 30,000 แรก = การย้ายเงินเดิมมาใช้
- 10,000 ส่วนเกิน = เงินทุนใหม่
- ยอดรวมกิจการใหม่ = 40,000
- เงินในลิ้นชัก = 40,000

## 4. จุดผิดของ implementation เดิม

เอกสารนี้บันทึกไว้เพื่อป้องกันการทำซ้ำ ไม่ใช่คำสั่งให้แก้ทันที:

1. `CashSession::openDay()` ใช้ยอดปิดวันก่อนเป็นยอดที่ต้องนับในลิ้นชักโดยตรง (`CashSession.php` ช่วงบรรทัด 122-135)
2. เมื่อนับเงินในลิ้นชักน้อยกว่ายอดรวม ระบบตีความเป็น variance และบังคับเหตุผล ทั้งที่อาจเป็นการเก็บเงินไว้ใน reserve
3. `CashDepositRequest::approve()` บันทึกเติมเงินเป็น `cash_movement direction=in` ทุกครั้ง จึงเพิ่มยอดรวมแม้เป็นการย้าย reserve เข้า drawer
4. `PurchaseOrder::createWithItems()` เรียก `assertOpen()` ก่อนตรวจ payment method ทำให้ PO ที่จ่ายผ่านธนาคารยังต้องเปิด cash session
5. `BusinessExpense` และ `SaleLot::recordRevenue()` มี coupling กับ cash session แม้เป็น `bank_transfer`
6. `cash_movements` เดิมมีเพียง `direction=in/out` ยังไม่สามารถระบุ source/destination ของการโอนภายในได้

## 5. แบบจำลองเป้าหมาย

ต้องแยกข้อมูลอย่างน้อยสองมิติ:

### 5.1 Cash position ledger

ตอบคำถามว่า “เงินของกิจการรวมเท่าไร และอยู่ที่ไหน”

ตำแหน่งระยะแรก:

- `drawer`
- `business_reserve` (รวม safe/Owner ไว้ก่อน เพื่อลด scope)
- `bank` (รองรับแยกเมื่อออกแบบ bank ledger)

### 5.2 Daily drawer session

ตอบคำถามว่า “วันนี้ลิ้นชักมีเงินเท่าไร ใครรับผิดชอบ และมีเงินเข้าออกอย่างไร”

ต้องแยก field/ความหมายของ:

- ยอดรวมกิจการ
- ยอดคงเหลือใน reserve
- ยอดคาดหมายใน drawer
- ยอดนับจริงใน drawer
- เงินทุนใหม่
- เงินที่โอนเข้า/ออก drawer
- variance ที่เป็นความผิดปกติจริง

การย้ายตำแหน่งเงินต้องไม่กระทบกำไรขาดทุน ส่วนซื้อ/ขาย/ค่าใช้จ่ายต้องเชื่อมกับ financial reports ตามธุรกรรมจริง

- การลบหรือแก้ historical production data โดยตรง

## 7. แผนการทำงานแบบ production-safe

1. เขียน technical design และ state/invariant table ให้ Owner ยืนยัน
2. สำรอง production database และสร้าง sandbox จาก backup
3. ออกแบบ migration แบบ additive และรักษา API เดิมให้ทำงานได้
4. เพิ่ม test scenarios ตามตัวอย่างในหัวข้อ 3
5. ทดสอบ payment method ที่เป็น cash และ bank transfer แยกกัน
6. ทดสอบ role cashier, manager, admin และ multi-branch
7. ทำ browser smoke test กับ flow ที่แคชเชียร์ใช้จริง
8. Owner ตรวจ sandbox และยืนยัน acceptance
9. backup production ซ้ำก่อน deploy
10. deploy migration + code แบบควบคุม และตรวจยอดก่อน/หลัง
11. monitor logs และหยุด rollout ทันทีเมื่อ invariant ใดผิด

ห้ามใช้ `reset-data.sql`, ห้ามแก้ migration เก่า และห้ามรัน SQL แก้ยอด production โดยไม่มี backup และ approval

## 8. Acceptance invariants

ทุก test และทุก deploy ต้องรักษากฎต่อไปนี้:

- การย้าย `drawer <-> business_reserve` ไม่เปลี่ยนยอดรวมกิจการ
- เงินทุนใหม่เพิ่มยอดรวมเฉพาะจำนวนที่เพิ่มจริง
- ซื้อ/ค่าใช้จ่ายเงินสดลดทั้งยอดรวมและเงินใน drawer ตามจริง
- รายรับเงินสดจาก Sale Lot เพิ่มทั้งยอดรวมและเงินใน drawer
- ธุรกรรม bank transfer ไม่ถูกบล็อกเพราะ drawer session ปิด
- เงินใน drawer ติดลบไม่ได้
- การปิดวันต้องบันทึกเงินที่ย้ายออกจาก drawer อย่างตรวจสอบย้อนหลังได้
- การเปิดวันด้วยเงินน้อยกว่ายอดรวมไม่ถือเป็น variance โดยอัตโนมัติ หากส่วนต่างอยู่ใน reserve
- historical records เดิมยังอ่านได้และไม่ถูกตีความใหม่โดยไม่มี cutover

---

## 9. Decisions ที่ต้องยืนยันก่อนเขียนโค้ด

- ตอนปิดวัน ระบบจะถือว่าย้ายเงินใน drawer ออกทั้งหมดโดยอัตโนมัติหรือให้กรอกยอดที่ย้ายจริง
- `business_reserve` จะรวมเงินในเซฟและกับ Owner เป็นก้อนเดียวในเฟสแรกหรือไม่
- เงินโอนธนาคารจะเริ่มมี bank balance ledger ในงานนี้ หรือให้แยกเป็น phase ถัดไป
- วันเริ่มใช้ cash-position model ใหม่ (cutover date)

จนกว่าจะยืนยัน decisions ส่วนนี้ ห้ามเริ่มแก้ production code
