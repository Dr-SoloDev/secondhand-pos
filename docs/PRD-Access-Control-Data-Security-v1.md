## 1. Problem Statement

ระบบ POS รับซื้อของเก่าที่กำลังจะขึ้น production มีสถาปัตยกรรมสิทธิ์การเข้าถึง (RBAC) 4 ระดับ (cashier, manager, super_manager, admin) ที่ implement ไว้แล้วในโค้ด แต่จากการตรวจสอบเทียบกับ spec สิทธิ์ที่เจ้าของระบบ (ผู้ว่าจ้าง) ต้องการจริง พบว่า **มีจุดที่โค้ดปัจจุบันให้สิทธิ์ไม่ตรงกับที่ต้องการ 4 จุด** และ **เลขบัตรประชาชนของผู้ขายเก็บเป็น plaintext ไม่มีการเข้ารหัส**

**หมายเหตุ (อัปเดตหลังยืนยันกับเจ้าของระบบ):** การที่ cashier ทุกสาขาเห็นข้อมูลผู้ขายข้ามสาขาได้ **เป็นความตั้งใจทางธุรกิจ ไม่ใช่ช่องโหว่** — เพราะร้านเป็นเจ้าของเดียวกันทุกสาขา ต้องใช้ระบบจดจำผู้ขายประจำ/แบล็คลิสต์/เทียร์ราคาให้เสมอภาคกันทุกสาขา ไม่งั้นลูกค้าจะรู้สึกว่าได้รับสิทธิพิเศษไม่เท่ากันในแต่ละสาขา จุดนี้จึงถูกตัดออกจาก requirement และแทนที่ด้วยการเสริม audit trail แทน (ดู P1-2 ใหม่)

ผลกระทบถ้าไม่แก้ก่อนขึ้น production:
- พนักงานทำงานไม่ได้ตามที่ควรจะทำได้ (เช่น cashier รับสต็อกเข้าสาขาตัวเองไม่ได้) → ต้องพึ่งผู้จัดการตลอดเวลา เพิ่มภาระงานและความล่าช้าในการดำเนินธุรกิจ
- ผู้จัดการสาขาไม่สามารถอนุมัติงานในขอบเขตของตัวเองได้ → คอขวดที่ต้องรอ admin/ผู้จัดการข้ามสาขาตลอด
- เลขบัตรประชาชนที่เก็บเป็น plaintext หลุดออกไปได้ง่ายกว่าที่ควรหากฐานข้อมูลรั่วไหล (แฮ็ก, backup หลุด, ดิสก์ถูกขโมย) — **ผู้พัฒนาและเจ้าของระบบมีความเสี่ยงทางกฎหมาย (PDPA) ร่วมกันหากข้อมูลรั่วไหล**

## 2. Goals

1. สิทธิ์การเข้าถึงในโค้ดตรงกับ spec ที่เจ้าของระบบกำหนดไว้ 100% ในทุก role (cashier / manager / super_manager / admin)
2. ข้อมูลอ่อนไหวของผู้ขาย (เลขบัตรประชาชน) ถูกเข้ารหัสที่ฐานข้อมูล ไม่ใช่ plaintext
3. ทุกการกระทำในระบบสามารถสืบค้นย้อนหลังได้ตามที่ระบุ (ช่วงวันที่ + ระดับสิทธิ์) ภายใน 1 หน้าจอ ไม่ต้องต่อ query เอง
4. ไม่มี endpoint ใดที่ผู้ใช้ role ต่ำกว่าที่ควรจะเข้าถึงข้อมูล/ฟังก์ชันของ role สูงกว่าได้ผ่านการเดา URL หรือแก้ parameter
5. เจ้าของระบบ (ผู้ว่าจ้าง) รับทราบและเซ็นรับ scope ที่ส่งมอบจริงเป็นลายลักษณ์อักษร ก่อนขึ้น production

## 3. Non-Goals (สิ่งที่ไม่รวมอยู่ใน scope นี้)

| ไม่รวม | เหตุผล |
|---|---|
| การเข้ารหัสข้อมูลทั้งฐานข้อมูล (full-disk/DB encryption) | เป็นงานระดับ infra/server ไม่ใช่ระดับ application — แนะนำแยกทำที่ layer ของ Ubuntu server/MySQL configuration |
| ระบบ 2FA / multi-factor authentication | ไม่ได้อยู่ใน scope ที่ตกลงไว้เดิม และ deadline ปัจจุบันไม่รองรับงานเพิ่มขนาดนี้ |
| การทำ data retention policy (ลบข้อมูลผู้ขายอัตโนมัติหลังพ้นระยะ) | เป็นประเด็นเชิงนโยบายที่ต้องคุยกับเจ้าของร้านและอาจต้องปรึกษาด้านกฎหมายก่อน ไม่ใช่แค่โค้ด |
| การปรับ UI/UX หน้าจอใหม่ตามสิทธิ์ (ซ่อนเมนูที่กดไม่ได้) | ควรทำต่อจาก backend fix นี้ในเฟสถัดไป ไม่ทำพร้อมกันเพื่อลดความเสี่ยง regression |
| **การจำกัดการมองเห็นข้อมูลผู้ขายตามสาขา** (เดิมคือ P1-2) | **ตัดสินใจแล้วโดยเจ้าของระบบ:** ร้านทุกสาขาเป็นเจ้าของเดียวกัน ต้องเห็นข้อมูลผู้ขาย/แบล็คลิสต์/เทียร์ราคาข้ามสาขาได้เพื่อความเสมอภาคของลูกค้าและป้องกันผู้ขายที่มีปัญหาหลบไปทำธุรกรรมสาขาอื่น พฤติกรรมปัจจุบันของโค้ด (มองเห็นได้ทุกสาขา) จึงถูกต้องตามที่ต้องการอยู่แล้ว ไม่ต้องแก้ |

## 4. User Stories (อ้างอิงจาก role spec ที่ได้รับ)

**Cashier / พนักงานหน้าร้าน**
- ในฐานะ cashier ฉันต้องการออกใบโอนสต็อกและรับสต็อกที่ส่งเข้าสาขาตัวเองได้ เพื่อไม่ต้องรอผู้จัดการทุกครั้งที่มีการโอนของระหว่างสาขา
- ในฐานะ cashier ฉันต้องการเพิ่ม/แก้ไขรายการแคทตาล็อกได้ เพื่อให้บันทึกสินค้าที่รับซื้อได้ครบถ้วนแบบเรียลไทม์หน้าร้าน
- ในฐานะ cashier ฉันต้องการกำหนดเทียร์บิลของผู้ขายได้ เพื่อให้ราคาที่เสนอลูกค้าหน้าร้านถูกต้องทันที ไม่ต้องรอผู้จัดการ

**ผู้จัดการรายสาขา**
- ในฐานะผู้จัดการสาขา ฉันต้องการอนุมัติคำขอยกเลิกใบรับซื้อของสาขาตัวเองได้ เพื่อไม่ต้องส่งเรื่องข้ามไปให้ admin หรือผู้จัดการข้ามสาขาทุกครั้ง

**Admin / Owner**
- ในฐานะ admin ฉันต้องการค้นหา log การกระทำทั้งหมดโดยกำหนดช่วงวันที่และ role ได้ เพื่อตรวจสอบย้อนหลังเมื่อเกิดข้อพิพาทหรือความผิดปกติ ได้อย่างรวดเร็วโดยไม่ต้องไล่ดูทีละหน้า

**ทุก role (ภาพรวมความปลอดภัยข้อมูล)**
- ในฐานะเจ้าของระบบ ฉันต้องการมั่นใจว่าเลขบัตรประชาชนของผู้ขายไม่ถูกเก็บเป็น plaintext เพื่อลดความเสียหายหากฐานข้อมูลรั่วไหล

## 5. Requirements

### 🔴 P0 — ต้องแก้ก่อนขึ้น production (Must-Have)

#### P0-1: ผู้จัดการรายสาขาต้องอนุมัติ/ปฏิเสธคำขอยกเลิก PO ของสาขาตัวเองได้

**สถานะปัจจุบัน:** `PurchaseOrdersController::approveCancellation()` และ `rejectCancellation()` จำกัดไว้ที่ `['admin', 'super_manager']` เท่านั้น — `manager` (ผู้จัดการรายสาขา) ไม่มีสิทธิ์แม้เป็นคำขอจากสาขาตัวเอง

**Acceptance Criteria:**
- [ ] Given ผู้ใช้ role `manager` ที่ผูกกับสาขา A, When เรียก `approveCancellation` สำหรับคำขอยกเลิก PO ของสาขา A, Then ระบบอนุมัติสำเร็จ
- [ ] Given ผู้ใช้ role `manager` ของสาขา A, When พยายามอนุมัติคำขอยกเลิก PO ของสาขา B, Then ระบบปฏิเสธด้วย 403
- [ ] Given ผู้ใช้ role `manager`, When อนุมัติ/ปฏิเสธสำเร็จ, Then มีการบันทึก `Logger::logActivity` เหมือนเดิม พร้อมระบุว่าอนุมัติโดย role ไหน

**ข้อควรระวังทางเทคนิค:** ต้องเพิ่มการเช็ค branch scope ในฟังก์ชันนี้ด้วย (ตอนนี้ยังไม่มี เพราะเดิมจำกัดเฉพาะ role ที่มองข้ามสาขาอยู่แล้ว) — ถ้าเพิ่ม `manager` เข้าไปโดยไม่เพิ่ม branch check จะกลายเป็นช่องโหว่ใหม่ทันที (ผู้จัดการสาขา A ไปอนุมัติคำขอของสาขา B ได้)

---

#### P0-2: Cashier ต้องเพิ่ม/แก้ไขรายการแคทตาล็อกได้

**สถานะปัจจุบัน:** `PurchaseItemCatalogController::createItem()` / `updateItem()` จำกัดที่ `['admin', 'manager']`

**Acceptance Criteria:**
- [ ] `cashier` เรียก `createItem`/`updateItem` สำเร็จ
- [ ] `deleteItem` **ยังคงจำกัดเฉพาะ `admin`** ตามเดิม (spec ไม่ได้ระบุให้ cashier ลบได้ — การลบเป็นความเสี่ยงสูงกว่าการเพิ่ม/แก้)
- [ ] มี audit log บันทึกว่า cashier คนไหนแก้ไขรายการอะไร เวลาไหน (ป้องกันข้อพิพาทเรื่องราคาภายหลัง)

---

#### P0-3: Cashier ต้องกำหนดเทียร์บิลผู้ขายได้

**สถานะปัจจุบัน:** ใน `SellersController::updateSeller()` การเปลี่ยน `tier_level` ถูกบังคับด้วย `requireAuth(['admin', 'manager'])` แม้ endpoint หลักจะเปิดให้ cashier เข้าได้

**Acceptance Criteria:**
- [ ] `cashier` เปลี่ยน `tier_level` ของผู้ขายได้สำเร็จ (ค่า 1-3 ตามเดิม)
- [ ] Audit log `update_seller_tier` ยังคงบันทึกครบตามเดิม รวมถึงระบุว่า cashier คนไหนเป็นคนเปลี่ยน

**ควรระวัง:** เนื่องจากเทียร์บิลกระทบราคาที่เสนอลูกค้าโดยตรง ควรพิจารณาว่าจะเปิดให้ cashier เปลี่ยนได้แบบไม่จำกัด หรือควรมี guardrail เพิ่ม (เช่น เปลี่ยนได้แต่ห้ามเปลี่ยนเทียร์ตัวเองให้ผู้ขายที่ตัวเองพึ่งรับซื้อมาในวันเดียวกัน เพื่อป้องกันการปั่นราคาให้พวกพ้อง) — เป็นคำถามเชิงนโยบายที่ควรถามเจ้าของระบบก่อนปล่อยแบบเปิดกว้างเต็มที่ (ดู Open Questions ข้อ 1)

---

#### P0-4: Cashier ต้องออกใบโอนสต็อกและยืนยันรับสต็อกเข้าสาขาตัวเองได้

**สถานะปัจจุบัน:** `StockTransfersController::store()` และ `confirm()` จำกัดที่ `['admin', 'manager', 'super_manager']` — cashier ถูกตัดออกจาก flow นี้ทั้งหมด นี่คือ gap ที่ใหญ่ที่สุดในบรรดา 4 จุด เพราะกระทบ operation ประจำวันโดยตรง

**Acceptance Criteria:**
- [ ] `cashier` ของสาขา A สร้างใบโอนสต็อก (`store`) ไปยังสาขา B ได้
- [ ] `cashier` ของสาขา B เรียก `confirm()` เพื่อยืนยันรับสต็อกที่ส่งมาจากสาขา A ได้ **เฉพาะรายการที่ปรากฏในระบบว่ากำลังรอสาขา B ตรวจรับเท่านั้น**
- [ ] Given ไม่มีข้อมูลใบโอนที่รอสาขา B ตรวจรับในระบบ (เช่น พนักงานขนส่งของมาส่งผิดสาขา), When cashier สาขา B พยายาม `confirm()` ใบโอนที่ไม่ใช่ของสาขาตัวเอง, Then ระบบต้องปฏิเสธและแสดงข้อความชัดเจนว่า "ไม่พบรายการรอตรวจรับที่สาขานี้ — กรุณาตรวจสอบว่าส่งของถูกสาขาหรือไม่" (ตรงตาม logic ที่ระบุใน spec)
- [ ] `cancel()`, `requestReversal()`, `approveReversal()`, `rejectReversal()` **ยังคงจำกัดที่ `admin/manager/super_manager` ตามเดิม** — spec ไม่ได้ให้สิทธิ์ cashier ยกเลิกหรือขอย้อนกลับใบโอนสต็อก มีแค่ออกใบกับรับของเท่านั้น

**ควรระวัง:** ฟังก์ชัน `confirm()` ปัจจุบันต้องตรวจสอบให้แน่ใจว่า branch scope check (คนที่รับต้องเป็นเจ้าของสาขาปลายทางเท่านั้น) มีอยู่แล้วก่อนเพิ่ม cashier เข้าไป — ถ้าโค้ดเดิมพึ่งพา role สูง (manager ขึ้นไป) เป็นตัวกรองแทน branch check ที่แท้จริง การเพิ่ม cashier เข้าไปตรงๆ อาจเปิดช่องให้ cashier สาขา A ไปยืนยันรับของที่จริงๆ ส่งไปสาขา B ได้ ต้อง verify จุดนี้ก่อน merge

### 🟠 P1 — ควรแก้ก่อน production แต่พอ negotiate เลื่อนได้ 1-2 วันหลัง launch ถ้าจำเป็นจริงๆ (Should-Have)

#### P1-1: เข้ารหัสเลขบัตรประชาชนผู้ขายที่ฐานข้อมูล (encryption at rest)

**สถานะปัจจุบัน:** คอลัมน์ `id_card` ในตาราง `sellers` เก็บเป็น plaintext ไม่มีการเข้ารหัสใดๆ ในโค้ดทั้งหมด (`Seller.php` และ helper files)

**เหตุผลที่เป็น P1 ไม่ใช่ P0:** ไม่ใช่ bug ที่ทำให้ระบบพังหรือคำนวณผิด — เป็นความเสี่ยงเชิงกฎหมาย/ความปลอดภัยข้อมูลที่ยังใช้งานได้ปกติระหว่างรอแก้ แต่ **ควรแก้โดยเร็วที่สุดหลัง launch ไม่ควรปล่อยค้างนาน**

**Acceptance Criteria:**
- [ ] `id_card` ถูกเข้ารหัสด้วย AES-256 ก่อนบันทึกลง DB และถอดรหัสตอนอ่านเพื่อแสดงผล/ค้นหา
- [ ] Encryption key เก็บแยกจากฐานข้อมูล (เช่น ใน `.env` ที่ไม่ commit เข้า git หรือ secret manager) — **ห้ามเก็บ key ไว้ในโค้ดหรือใน migration file เด็ดขาด**
- [ ] ฟังก์ชันค้นหาผู้ขายด้วยเลขบัตร (`findByIdCard`, `searchSellers`) ยังทำงานได้ถูกต้องหลังเข้ารหัส (ต้องออกแบบให้ค้นหาได้ เช่น เก็บ hash แยกไว้สำหรับค้นหา + เก็บค่าเข้ารหัสไว้สำหรับแสดงผล)
- [ ] มี migration script แปลงข้อมูลเดิมที่เป็น plaintext อยู่แล้วให้เป็นแบบเข้ารหัสทั้งหมด แบบ one-time run บน production

**ข้อควรระวังสำคัญ:** ถ้าทำ hash แบบทางเดียว (one-way hash) เพื่อการค้นหา จะไม่สามารถกู้ค่าเดิมกลับมาแสดงผลได้ ต้องแยกให้ชัดระหว่าง "ค่าที่ใช้ค้นหา" (hash, ทางเดียว) กับ "ค่าที่ใช้แสดงผล" (encrypted, ถอดรหัสกลับได้) — เขียนผิดจุดเดียวอาจทำให้ข้อมูลเดิมกู้คืนไม่ได้ถาวร ต้อง backup ฐานข้อมูลเต็มรูปแบบก่อนรัน migration นี้ทุกครั้งไม่มีข้อยกเว้น

---

#### P1-2: Audit trail สำหรับการเปิดดูข้อมูลผู้ขาย (seller PII view log)

**ที่มา:** เดิมข้อนี้คือ "จำกัดการมองเห็นข้อมูลผู้ขายตามสาขา" แต่เจ้าของระบบยืนยันแล้วว่าการเห็นข้ามสาขาเป็นความต้องการทางธุรกิจจริง (ดู Non-Goals ข้อ "การจำกัดการมองเห็นข้อมูลผู้ขายตามสาขา") จึงปรับ requirement ใหม่: **เมื่อทุกคนเห็นข้อมูลทุกสาขาได้แบบไม่มี branch เป็นตัวกรองอีกชั้น การรู้ว่า "ใครเปิดดูข้อมูลรายไหน เมื่อไหร่" จึงสำคัญขึ้นกว่าเดิม** เพื่อให้สืบย้อนกลับได้หากเกิดข้อพิพาทหรือมีการนำข้อมูลไปใช้ผิดวัตถุประสงค์

**สถานะปัจจุบัน:** `getSeller()`, `getSellerDataCenter()`, `viewPhoto()` ไม่มีการบันทึก log ว่าใครเปิดดูข้อมูลผู้ขายรายไหน (ต่างจาก `updateSeller()` ที่มี `Logger::logActivity` อยู่แล้วเวลาแก้ไขข้อมูล — แต่การ "ดู" ยังไม่ถูกบันทึก)

**Acceptance Criteria:**
- [ ] ทุกครั้งที่มีการเรียก `getSeller()` หรือ `getSellerDataCenter()` บันทึก log ด้วย `Logger::logActivity()` ระบุ user_id ที่เปิดดู, seller_id ที่ถูกดู, เวลา
- [ ] ทุกครั้งที่มีการเรียก `viewPhoto()` (ดูรูปบัตรประชาชน) บันทึก log แยกประเภทชัดเจน (เช่น `view_seller_id_card_photo`) เพราะเป็นข้อมูลอ่อนไหวกว่าข้อมูลทั่วไป
- [ ] `getSellers()` (ดึงรายการทั้งหมด) และ `searchSellers()` **ไม่ต้อง log ทุกครั้ง** (จะรกเกินไปเพราะเป็น endpoint ที่เรียกบ่อยเพื่อ autocomplete) — log เฉพาะการเปิดดูรายละเอียดรายบุคคล (`getSeller`/`getSellerDataCenter`/`viewPhoto`) ก็เพียงพอ
- [ ] Log เหล่านี้ค้นหาได้ผ่าน endpoint audit log เดียวกับ P1-3 ด้านล่าง (ใช้ `role`/`date range` filter ร่วมกันได้)

**ควรระวัง:** การ log ทุกครั้งที่เปิดดูข้อมูล อาจทำให้ตาราง `activity_log` โตเร็วกว่าที่คาด (ต่างจาก log เฉพาะตอนแก้ไขข้อมูลซึ่งเกิดไม่บ่อย) ควรพิจารณาทำ index ที่เหมาะสมบน `(action, created_at)` และอาจต้องมีนโยบาย archive log เก่าในอนาคต (ยกเป็น P2 แยกได้ถ้าจำเป็น)

---

#### P1-3: เพิ่ม filter ช่วงวันที่และ role ในหน้าค้นหา Activity Log

**สถานะปัจจุบัน:** `ActivityLog::getLogsWithPagination()` และ endpoint `getActivityLog()` filter ได้แค่ `user_id` เท่านั้น ไม่มี date range ไม่มี role filter ตามที่ spec ต้องการ

**Acceptance Criteria:**
- [ ] เพิ่ม parameter `start_date`, `end_date` (กรองจาก `created_at`)
- [ ] เพิ่ม parameter `role` (join กับตาราง `users` กรองด้วย `users.role`)
- [ ] ทั้งสอง filter ใช้ร่วมกับ `user_id` เดิมได้ (AND condition ไม่ใช่แทนที่กัน)
- [ ] Endpoint ยังคงจำกัดเฉพาะ `admin` เท่านั้นตามเดิม (ไม่เปลี่ยน permission เดิม)
- [ ] ผลลัพธ์ยัง paginate ได้เหมือนเดิม ไม่โหลดข้อมูลทั้งหมดมาแล้ว filter ฝั่ง frontend (จะช้าเมื่อข้อมูลเยอะ)

### 🟡 P2 — Future Considerations (ไม่ต้องทำตอนนี้ แต่ควรออกแบบไม่ให้ขวางทางในอนาคต)

- **Data retention / auto-purge ผู้ขายที่ไม่มีธุรกรรมนานเกิน N ปี** — ต้องตัดสินใจร่วมกับเจ้าของระบบเรื่องนโยบายก่อน ไม่ใช่แค่โค้ด
- **Field-level permission แบบละเอียดกว่า role** (เช่น cashier เห็นชื่อ-เบอร์โทรผู้ขายได้ แต่เห็นเลขบัตรแบบ mask บางส่วนเท่านั้น เช่น `1-XXXX-XXXXX-XX-X`) — ออกแบบไว้เผื่ออนาคตแต่ยังไม่ทำตอนนี้ เพราะกระทบ UI เยอะและต้องคุยกับเจ้าของระบบก่อนว่าจำเป็นแค่ไหน
- **แจ้งเตือนอัตโนมัติเมื่อมีการเข้าถึงข้อมูลผู้ขายจำนวนมากผิดปกติในเวลาสั้นๆ** (anomaly detection เบื้องต้น) — ป้องกันกรณีพนักงานคนใดคนหนึ่ง export/ดูข้อมูลจำนวนมากผิดปกติ

## 6. Risks & Safeguards (สิ่งที่ควรระวัง และควรป้องกัน)

### ความเสี่ยงเชิงเทคนิค

| ความเสี่ยง | ผลกระทบถ้าเกิดขึ้นจริง | วิธีป้องกัน |
|---|---|---|
| เพิ่ม role ใหม่เข้า endpoint โดยไม่เช็ค branch scope ให้ครบ (โดยเฉพาะ P0-1 และ P0-4) | เปิดช่องให้ผู้ใช้ role ต่ำเข้าถึงข้อมูล/อนุมัติงานข้ามสาขาโดยไม่ตั้งใจ — แย่กว่าที่เป็นอยู่ตอนนี้ | เขียน test case เฉพาะสำหรับ "role ที่ถูกต้อง + สาขาผิด → ต้องถูกปฏิเสธ" ทุกจุดที่แก้ ไม่ใช่แค่เทสว่า "role ถูก + สาขาถูก → สำเร็จ" |
| รัน migration เข้ารหัส `id_card` (P1-1) แล้วเกิดข้อผิดพลาดระหว่างแปลงข้อมูล | ข้อมูลเลขบัตรประชาชนเดิมกู้คืนไม่ได้ถาวร กระทบผู้ขายจริงที่มีประวัติอยู่แล้ว | Backup DB แบบเต็มก่อนรันทุกครั้ง + ทดสอบ migration บน environment staging ที่มีข้อมูลจำลองก่อน ไม่รันตรงบน production ครั้งแรก |
| แก้ permission หลายจุดพร้อมกันในรอบเดียวใกล้ deadline | ความเสี่ยง regression สูง เพราะพี่ทำงานคนเดียว ไม่มีคนช่วย review | แก้ทีละจุด, รัน automated test ที่มีอยู่แล้ว (`tests/api/`) ทุกครั้งหลังแก้แต่ละจุด ก่อนไปจุดถัดไป |

### ความเสี่ยงเชิงกฎหมาย/ธุรกิจ

- **ความรับผิดของผู้พัฒนา:** อย่างที่พี่กังวลไว้เอง หากข้อมูลอ่อนไหว (เลขบัตรประชาชน) รั่วไหลจากระบบที่พี่พัฒนา ผู้พัฒนาอาจถูกดึงเข้าไปมีส่วนรับผิดร่วมกับเจ้าของระบบตาม PDPA ได้ — ผมไม่ใช่ทนายและให้คำแนะนำทางกฎหมายที่ชัดเจนไม่ได้ แต่ในทางปฏิบัติ **การมีเอกสารนี้เป็นลายลักษณ์อักษรที่ระบุว่าอะไรทำแล้ว อะไรยังไม่ทำ และเจ้าของระบบรับทราบ** คือสิ่งที่ช่วยป้องกันพี่ได้มากที่สุดในเชิงหลักฐาน ไม่ใช่การพยายามทำทุกอย่างให้สมบูรณ์ 100% ก่อนส่ง
- **แนะนำ:** ก่อน launch ส่งเอกสารสรุปสั้นๆ (ไม่ต้องเป็น PRD เต็มแบบนี้) ให้เจ้าของระบบเซ็นรับทราบว่า P1-1 (เข้ารหัสเลขบัตร) และ P1-2 (audit trail การเปิดดูข้อมูลผู้ขาย) จะตามมาในสัปดาห์แรกหลัง launch ไม่ใช่วันแรก — ป้องกันไม่ให้ภายหลังเจ้าของระบบอ้างว่า "ไม่รู้ว่ายังไม่ได้ทำ" ควรระบุในเอกสารเดียวกันด้วยว่าการเห็นข้อมูลผู้ขายข้ามสาขาเป็นการตัดสินใจทางธุรกิจของเจ้าของระบบเอง (มีบันทึกไว้ในเอกสารนี้) ไม่ใช่ default ที่ผู้พัฒนาเลือกเอง — ป้องกันข้อโต้แย้งย้อนหลังว่า "ทำไมข้อมูลถึงเห็นข้ามสาขาได้"

## 7. Success Metrics

**Leading indicators (วัดได้ทันทีหลังแก้):**
- 0 endpoint ที่ role เข้าถึงผิดขอบเขต spec (วัดจาก automated test ที่เขียนเพิ่ม)
- 100% ของ P0 requirements ผ่าน acceptance criteria ก่อน deploy ขึ้น production

**Lagging indicators (วัดใน 30 วันแรกหลัง launch):**
- 0 incident เรื่องข้อมูลผู้ขายรั่วไหลหรือถูกเข้าถึงผิดสิทธิ์
- จำนวนครั้งที่ cashier ต้องรอผู้จัดการอนุมัติงานที่ตอนนี้ทำเองได้แล้ว (โอนสต็อก, แคทตาล็อก, เทียร์บิล) ควรลดลงจากที่เคยเป็นปัญหาก่อนแก้

## 9. Timeline & Phasing

**ก่อน launch (วันนี้-พรุ่งนี้):** P0-1 ถึง P0-4 ทั้งหมด — เป็น pure permission fix ใน controller ไม่กระทบ schema ไม่กระทบข้อมูลเดิม ความเสี่ยงต่ำ ทำได้เร็ว ควรรวมอยู่ใน release เดียวกับที่จะขึ้น production

**สัปดาห์แรกหลัง launch:** P1-3 (audit log filter) — ไม่กระทบ user-facing feature ทำแยกได้โดยไม่ต้องหยุดระบบ

**ภายใน 2 สัปดาห์หลัง launch:** P1-1 (เข้ารหัส id_card) — ต้องทำ staging test ก่อนอย่างจริงจังเพราะกระทบข้อมูลเดิมและมี migration risk ตามที่ระบุใน Risks & Safeguards ส่วน P1-2 (audit trail การเปิดดูข้อมูลผู้ขาย) ทำพร้อมกับ P1-3 ได้เลยเพราะเป็นแค่การเพิ่ม log ไม่กระทบข้อมูลเดิม ความเสี่ยงต่ำกว่า P1-1 มาก

**ไม่กำหนดเวลา (P2):** รอ business decision จากเจ้าของระบบก่อน
